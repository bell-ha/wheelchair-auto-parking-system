# UWB 거리 측정 원리 정리

이 폴더의 펌웨어(`uwb_tag` / `uwb_anchor`)가 실제로 하는 일을 기준으로 정리했다.
숫자는 라이브러리 상수와 2026-10-29 첫 측정에서 확인한 것이다. 출처는 맨 아래.

> **한 줄 요약** — 태그가 신호를 보내고 앵커가 정해진 시간 뒤에 답한다.
> 태그는 "왕복에 걸린 시간 − 앵커가 기다린 시간"의 절반으로 전파가 날아간 시간을 구하고, 거기에 빛의 속도를 곱한다.

---

## 1. 무엇과 무엇 사이의 거리인가

- 두 보드의 **흰색 칩 안테나(UWB4A)끼리의 직선거리**다. 보드 중심도, ESP32도 아니다.
  엄밀히는 안테나 안쪽의 한 점(위상 중심)이라, 줄자는 **안테나 칩 중심끼리** 잰다.
- **방향은 모른다.** 이 보드는 안테나가 하나라 각도를 못 잰다(PDoA 불가).
  앵커 하나로 아는 것은 "앵커에서 반지름 d인 **구(球)** 위 어딘가"뿐이다.

## 2. 위아래도 포함되나 — 그렇다

직선거리라 높이 차이가 그대로 들어간다.

```
측정 거리 d = √(수평거리² + 높이차²)        수평거리 = √(d² − 높이차²)
```

높이 차이 때문에 **더 길게** 나오는 양:

| 높이차 \ 수평거리 | 0.5 m | 1 m | 2 m | 3 m | 5 m |
|---|---:|---:|---:|---:|---:|
| 0.3 m | +8.3 cm | +4.4 cm | +2.2 cm | +1.5 cm | +0.9 cm |
| 0.5 m | +20.7 cm | +11.8 cm | +6.2 cm | +4.1 cm | +2.5 cm |

**가까울수록 커진다.** 주차는 가까운 거리에서 끝나므로 무시할 수 없다.

- 실험에서는 앵커와 태그 안테나를 **같은 높이**에 둔다. 아니면 높이를 재서 위 식으로 수평거리를 구한다
- V3 설치에서는 앵커(차)와 태그(휠체어) 안테나 **높이를 기록해 둔다**. 위치 계산에 들어간다

## 3. 어떻게 재나 — SS-TWR (단방향 양방향 측정)

```
  태그 (uwb_tag)                          앵커 (uwb_anchor)
    T1 ──── poll ─────────────────────▶ T2
                                         │  정확히 0.9 ms 기다렸다가 (예약 송신)
    T4 ◀─────────────────── response ── T3     T2, T3를 실어 보냄

  왕복   Rtd_init = T4 − T1      ← 태그 시계로 잼
  대기   Rtd_resp = T3 − T2      ← 앵커 시계로 잼
  비행   ToF = (Rtd_init − Rtd_resp) / 2
  거리   d = ToF × 299,702,547 m/s   (공기 중 빛의 속도)
```

- **두 보드의 시계를 맞출 필요가 없다.** 각자 자기 시계로 잰 **시간 간격**만 쓰기 때문이다. 이게 TWR의 핵심이다
- **얼마나 정밀해야 하나.** 빛은 1 ns에 30 cm 간다. DW3000 시계 1틱 = 15.65 ps = 빛이 **4.69 mm** 가는 시간.
  0.5 m라면 비행시간은 약 1.7 ns다. 이걸 0.9 ms 기다림 속에서 골라내는 셈이다
- 태그는 10 Hz로 이걸 반복한다(`RNG_DELAY_MS 100`). 화면의 앵커 "10 회/초"가 그 응답 수다

### 왜 UWB여야 하나

- 펄스가 아주 짧고(약 2 ns) 대역이 넓다(채널 5: 6.5 GHz 중심, 약 500 MHz 폭) → **도착 순간이 날카로워** 시간을 잴 수 있다
- 같은 이유로 **직진파와 반사파가 시간상 갈라진다.** 칩이 가장 먼저 온 경로(first path)를 골라 쓰므로 벽·차체 반사에 덜 속는다
- BLE·Wi-Fi의 신호 세기 방식은 세기로 거리를 짐작하므로 미터 단위로 흔들린다

## 4. 오차는 어디서 오나

| 원인 | 크기 | 우리 대처 |
|---|---|---|
| **시계 속도 차이** — 보드마다 수정발진기가 조금씩 다르게 돈다 (ppm) | 보정하지 않으면 ≈ 응답 대기 × ppm ÷ 2 × 빛의 속도. 0.9 ms 기준 **1 ppm 13 cm · 3 ppm 40 cm · 20 ppm 2.7 m** | 태그가 수신 신호의 반송파로 시계 차이를 재서 보정한다 (`clk_ppm` 열). 첫 측정 표준편차 1.8 cm → 보정이 동작한다. 더 줄이려면 DS-TWR(메시지 3개) |
| **안테나 지연** — 신호가 칩·안테나 회로를 지나는 시간. 기본값 16385틱 = 256 ns | 거리와 무관한 **고정 오차**. 양쪽 보드의 TX·RX 지연 4개를 모두 1틱씩 바꾸면 거리가 9.4 mm 바뀐다 | 실험 1에서 추정 (`analyze_range.py`). 보드별 값은 **보드 3개로 쌍마다 재서**(A+B, B+C, A+C) 푼다 |
| **안테나 방향** | 방향에 따라 유효 지연이 달라진다 | 실험할 때는 방향을 고정. 영향은 따로 잰다 |
| **높이 차이** | 2절 표 | 같은 높이 또는 계산 |
| **가림 (NLOS)** — 차체·사람 몸 | 직진파가 약해지거나 막혀 반사파로 잰다 → **항상 길게** 나오고 실패가 는다 | RX−FP로 판별 (5절) |
| **XTRIM 미보정** — 호환 모듈이라 시계 보정값이 비어 있음 | 시계 차이(ppm)가 커질 수 있다 → 첫 줄로 이어짐 | 반송파 보정이 흡수한다. `clk_ppm`을 보고 판단 |

## 5. 신호 세기 진단 — RX와 FP

태그는 응답을 받을 때마다 수신 진단값을 같이 보낸다. 환산은 [tools/uwb_proto.py](tools/uwb_proto.py)에서 한다.

| | 뜻 |
|---|---|
| **RX** | 전체 수신 세기 (직진파 + 반사파) |
| **FP** | 첫 경로(직진파) 세기 |
| **RX − FP** | 작으면 직진파가 대부분 → 트여 있음(LOS). 크면 반사파 위주 → 가려짐(NLOS) |

- 기준값: DW1000 매뉴얼은 **6 dB 미만 LOS, 10 dB 초과 NLOS**로 안내한다고 알려져 있다. DW3000용 기준은 공개 자료가 없어 **실험 1에서 우리 데이터로 정한다**
- 첫 측정(가까이 둔 상태)은 **0.9 dB**였다
- 이 값 덕분에 공식 하나가 확인됐다. F1~F3를 4로 나누지 않으면 −11 dB가 나와 "직진파가 전체보다 세다"는 불가능한 값이 된다 → 4로 나누는 게 맞다

## 6. 연결 구조 — 맥북은 무엇을 하나

```
  [DFBB 앵커]  )))  UWB 무선 6.5 GHz  (((  [DFCA 태그]
       │ USB: 전원 5 V + 시리얼                  │ USB: 전원 5 V + 시리얼
       └───────────────── 맥북 ──────────────────┘
                live_view.py가 두 포트를 읽어 화면에 표시
```

- **거리는 두 보드가 무선으로 직접 잰다.** 맥북은 중계하지 않는다
- USB는 **전원과 데이터 둘 다** 실어 나른다. 태그는 측정마다 한 줄을 보내고, 앵커는 1초마다 응답 수를 보낸다
- 확인하는 법: 앵커를 보조배터리로 옮겨도 태그 거리는 계속 나온다(앵커 카드만 '뽑힘'으로 바뀜)
- 실제 설치: 앵커는 **전원만** 있으면 된다(보조배터리·차량 USB). 태그 데이터는 Jetson에 USB로 보내거나 ESP32의 Wi-Fi/BLE로 보낸다

### 와이파이 없이 어떻게 통신하나

DW3000은 거리 센서이기 전에 **무선 송수신기**다. 무전기처럼 같은 채널의 기기끼리 6.5 GHz로 바로 주고받는다.
공유기·페어링·인터넷이 필요 없고, ESP32의 Wi-Fi/BLE는 지금 쓰지 않는다
(ESP32는 DW3000에 명령을 주고 결과를 USB로 보내는 역할만).

서로를 알아보는 조건은 두 가지다.

| 조건 | 내용 | 어디에 |
|---|---|---|
| 무선 설정이 같다 | 채널 5, 프리앰블 코드 9, 6.8 Mbps … 다르면 신호를 아예 못 잡는다 | 두 `.ino`의 `config` |
| 메시지 양식이 맞다 | IEEE 802.15.4 데이터 프레임 모양. 네트워크 번호 `0xDECA` + 고정 주소 2개 + 기능 코드 | `tx_poll_msg` / `rx_resp_msg` |

| 메시지 | 방향 | 크기 | 내용 |
|---|---|---|---|
| poll | 태그 → 앵커 | 12바이트 | 머리 + 기능 `0xE0` + 오류검사(CRC) |
| response | 앵커 → 태그 | 20바이트 | 머리 + 기능 `0xE1` + **poll 받은 시각(T2) + 응답 보낸 시각(T3)** + CRC |

앵커는 양식이 맞는 poll에만 답하고, 태그도 양식이 맞는 응답만 받는다. 다른 펌웨어의 신호는 무시된다.
실어 나르는 건 사실상 시각 두 개라 메시지가 짧고, 왕복이 1 ms 안에 끝난다.

**지금은 짝 구분이 없다.** 앵커를 2개 이상 켜면 poll 하나에 전부 동시에 답해 전파가 겹친다.
앵커를 늘릴 때는 앵커마다 번호를 주고 차례로 답하게(TDMA) 바꿔야 한다 — Makerfabs `Multi Anchor + Multi Tag` 예제 방식.

## 7. 우리 설정값의 뜻

| 항목 | 값 | 뜻 |
|---|---|---|
| 채널 | 5 (6.5 GHz) | DW3000은 5와 9(8 GHz)를 지원. 앵커·태그가 같아야 한다 |
| 프리앰블 | 128 심볼, 코드 9 (PRF 64 MHz) | 수신기가 신호를 잡고 도착 시각을 추정하는 앞부분. 길수록 멀리·잡음에 강하지만 느리다 |
| 데이터율 | 6.8 Mbps | 메시지가 짧아 왕복이 빨리 끝난다 |
| 응답 대기 | 0.9 ms | 짧을수록 시계 차이 영향이 줄지만, 너무 짧으면 앵커가 준비를 못 해 예약 송신이 실패한다 |
| 측정 주기 | 100 ms (10 Hz) | 앵커 하나 기준. 앵커가 늘면 차례로 재야 해서 앵커당 주기가 길어진다 |

## 8. 거리에서 위치로 (다음 단계)

| 앵커 수 | 알 수 있는 것 |
|---|---|
| 1 | 거리만 (구 위 어딘가) |
| 2 | 바닥 위 두 점 중 하나 — 어느 쪽인지 모른다 |
| **3** | **바닥 위 한 점 (2D 위치)** — 원 3개의 교점 |
| 4 이상 | 높이까지(3D), 또는 2D를 더 안정적으로 |

- 휠체어가 **어느 쪽을 보는지(방위)는 UWB로 안 나온다.** IMU가 맡는다
- 앵커·태그의 설치 높이가 다르면 2절대로 높이를 넣어 푼다
